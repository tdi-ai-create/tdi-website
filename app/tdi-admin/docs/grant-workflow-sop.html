Grant Workflow

How a grant narrative gets written, checked, approved and submitted, and who owns it at each point.

Updated 1 September 2026. Living document, extended as each phase ships.

Every rule below is stated as a condition and a consequence, because the failures we have had were never broken code. They were rules nobody had written down, so each screen and each route invented its own and they quietly disagreed.

Where the rules actually live

lib/funding-rules.ts. That file is the source, this page is the explanation. If the two ever disagree, the file is right and this page is stale, so fix the page.

The path

not_started→ requested→ qa_review→ approval→ ready

With one detour. If QA fails three times the narrative goes to escalated and waits for a person to choose what happens next.

Goes loud means the item stops reading as normal waiting on the Needs You board and becomes high urgency owned by a person. It does not chase anyone automatically. It stops the portal telling you everything is fine.

not_started and ready have no limit on purpose. Both can legitimately wait on an application window or a school's timing.

The rules

If you request a draft, then the narrative becomes requested and the agent you chose is assigned.

If a narrative is requested and the funding window is open and the school's gate is open and the pursuit is not archived, then it appears in the writer's queue. If any one of those is false it is invisible to every agent, and the board says so rather than pretending someone is working on it.

If a draft arrives, then it moves to qa_review and a message goes to Slack.

If QA passes, then it becomes approval and Bella is at-mentioned. A pass never reaches a school on its own.

If QA fails on the first or second attempt, then it returns to requested and Julie's summary becomes the writer's guidance.

If QA fails a third time, then it becomes escalated and the reviewer must attach a diagnosis with concrete options. An escalation without options is refused, because Bella is never handed an open problem.

If a QA failure arrives without an explanation of at least fifteen characters, then the whole review is rejected. A fail nobody can act on is worse than no fail.

If the QA review row cannot be written, then nothing advances. A narrative never moves on the strength of a review that was not recorded.

If Bella approves, then it becomes ready and is waiting to be submitted.

If Bella sends it back from approval, then it returns to requested, her note becomes the writer's guidance, and the QA pass that got it there is retired so the row cannot sit in requested still claiming it passed.

If Bella sends it back with direction from an escalation, then it returns to requested, her note becomes the guidance, and the attempt count resets so QA reviews the new version fresh.

When QA finds something a writer cannot fix

A review returns a list, and every item says who can close it. Some are things the writer fixes by rewriting. Others cannot be fixed by writing at all, because the information does not exist yet and a person has to go and get it.

If every item can be fixed by rewriting, then the narrative goes back to the writer with those items as their guidance, and it counts as one of their two attempts.

If some items need a person and some do not, then the writer still gets everything they can fix, and their guidance contains only those items. They are never handed something they cannot do.

If nothing is left that rewriting can fix, then it parks with the ask already written out and a recommendation to go and get it. This does not spend one of the writer's attempts, because they were never able to fix it. Burning their attempts on something impossible is how a narrative reaches escalation with no useful options.

Why this matters more than it sounds. Before this, one verdict covered the whole narrative. A single item needing a person marked the whole thing blocked, the writer read that as stop, and every item they could have fixed waited on the slowest one. Everything waited on the hardest thing rather than on itself.

Until the QA rubric starts tagging its findings, reviews arrive untagged and every item is treated as the writer's, which is exactly how the system behaved before. Nothing changes until the tagging starts.

She never does QA

Julie owns QA end to end and is the only reviewer. No screen offers Bella a pass or fail control, and no code path creates a QA task owned by her. Her two jobs are approving, meaning is this true about this school and does it sound like us, and choosing between concrete options when something escalates.

Notifications

Messages go to #grant-work. A message names the school, says what happened, at-mentions the person who owes the next move, and links straight to the item: the link opens the right section and marks the row it is about, rather than dropping you on a page with everything collapsed.

A state with a human owner should tell that human when it happens. The daily digest is a backstop for things nobody acted on, not the way people are supposed to find out.

The failure this exists to prevent

Two St. Peter Chanel narratives failed QA on 24 August with two items that needed a phone call, an EIN and a confirmation of how the parish handles equitable services, and roughly eight items that needed nobody, including a missing client package and a style violation.

Both items were marked blocking, the writer read that as stop, and all ten sat untouched for eight days while the board reported it as ordinary waiting.

Nothing was broken. The rule for what to do when part of the feedback needs a human had never been written down, so the writer invented the most cautious one available.
